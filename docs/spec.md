# Leonida Field Guide: build spec

The goal: a player opens this on a phone or tablet beside the console, gets an answer in two taps, and never sees a spoiler they did not ask for. It also works on desktop.

This spec is the contract. Where it is silent, pick the smallest thing that works and say so in your report.

## What it is not

- No story content, at any setting. No mission names, plot, character fates or endings, anywhere in the repo.
- No interactive map. Link to one (see "Links out").
- No accounts, no ads, no analytics, no trackers. The only cookies are the gate token and the spoiler-level word (see "Access gate"). Synced ticks are a single shared record behind the password gate, not an account: no sign-up, no user ids, no per-person data. Settings never sync. The About screen says exactly this.
- No Rockstar logos, artwork, screenshots, fonts or trade dress. The footer says the site is unofficial.
- No copied guide text. Restate each fact in our own words and link the source.
- No web fonts and no UI framework. No runtime dependency ships to the browser.

## Stack

- Astro, static output, deployed by Vercel on push to `main` (the project is already linked). Check the current Astro docs through context7 before scaffolding.
- Content is data: one file per answer in an Astro content collection, validated by a schema. A record that fails the schema fails the build.
- Multi-page site. Navigation is plain links, with cross-document view transitions as an enhancement. The pages work with JavaScript off, except the things listed under "Needs JavaScript".
- Vanilla CSS with custom properties, and small vanilla JS modules. Tests use Playwright and axe.

## Data shape

```ts
type Tier = 'none' | 'places' | 'mild';            // there is no 'story' tier
type Console = 'ps5' | 'xbox-x' | 'xbox-s';
type Topic = 'setup' | 'settings' | 'controls' | 'saving' | 'money'
           | 'getting-around' | 'bonuses' | 'fixes' | 'good-to-know' | 'places';
type Stage = 'before' | 'hour-1' | 'day-1' | 'week-1';

type Answer = {
  id: string;                    // slug, stable for ever (checklists store it)
  question: string;              // plain words, as a player would ask it
  short: string;                 // the answer in at most 240 characters
  body?: string;                 // markdown, optional detail
  topic: Topic;
  stage: Stage;
  tier: Tier;                    // the tier of the whole record, title included
  consoles: Console[] | 'all';
  byConsole?: Partial<Record<Console, string>>;   // replaces `short` for that console
  confidence: 'official' | 'reported' | 'community';   // of the whole record; with `basis`, the weakest claim's (filters read this)
  basis?: { claim: string; confidence: 'official' | 'reported' | 'community' }[];   // at least 2: a record that mixes sources of different standing says per claim which is which (see "Confidence labels")
  sources: { url: string; title: string; console?: Console | Console[] }[];   // at least one; `console` on a source made for one console family only (see "Source console")
  checked: string;               // ISO date the sources were last checked
  rank?: number;                 // 1 = most asked; drives "Most asked"
  order?: number;                // to-dos only: lower first within a stage, by what depends on what (see "Console", One order)
  todo?: string;                 // if set, the record is a checklist item with this label
  keywords?: string[];           // up to 20 short strings (40 characters each): words players use that the text does not
  reveal?: { tier: Exclude<Tier, 'none'>; text: string; label?: string }[];  // hidden details inside a 'none' answer; `label` (at most 80 characters) is the control's text at Off, so it is generic and holds none of `text`
};
```

Rules the schema or the checks enforce:

- `confidence: 'official'` requires a source on rockstargames.com, support.rockstargames.com, take2games.com, playstation.com or xbox.com that a person or agent opened and read. Otherwise use `reported`.
- A `places` or `mild` record's `question`, `short`, `body`, `todo` and `keywords` are all hidden text. So is every `reveal[].text`. The `keywords` of a `none` record are not hidden. They sit only in the search index and are never shown on a page. Hidden text may appear only in a tier's explicit-show pages (`/<tier>/<id>/show/`, `/places/list/show/`), its `/h/<tier>/` files (fragments, search index, offline list) and nowhere else, a gate page's title, meta tags, headings, labels and links included (see "The spoiler dial").
- `topic: 'places'` implies `tier: 'places'`.
- **Confidence labels.** `official`: the claim was read on rockstargames.com, support.rockstargames.com, take2games.com, playstation.com or xbox.com. `reported`: news, guides and creators, and any claim we could not read on an official page. `community`: forums and player posts only; a news site or a console maker is never `community`. A page that returned no text is never a source for a claim.
- **A label per claim (fix round 8).** Where one answer mixes sources of different standing (an official page for one claim, a news report for another), the optional `basis` field names the claims and each one's label, for example `{ claim: 'the space the game needs', confidence: official }` and `{ claim: "a 512 GB Series S's usable space", confidence: reported }` (a claim is at most 80 characters, written to follow "How sure we are:" after a capital). The schema (`src/content.config.ts`, `basisProblems()` in `src/data/confidence.js`) rejects an unknown label, an `official` claim with no source on an official host, a `reported` or `community` claim with only official-host sources, and a record whose own `confidence` is not its weakest claim. The answer page then shows the claims in the label line instead of one badge: "How sure we are: The space the game needs, official (from the publisher or platform); a 512 GB Series S's usable space, reported (from news sites or creators)." with the "What does this mean?" disclosure giving the meaning of each label used (the About page's definitions, from the same `confidence.js`). A record with no `basis` shows its one badge as before. `tests/content/basis.test.mjs` fails a record that mixes official-host and other sources without `basis`, unless it is listed there with the reason one label is true; the build refuses a bad `basis` (it runs the real schema).
- **Console text.** `consoles: all` text (question, `short` where there is no `byConsole`, `body`, `todo`, `reveal`) names no console and uses no console's button names, except as the tokens `{cross}` `{circle}` `{square}` `{triangle}` `{l1}` `{r1}` `{l2}` `{r2}` `{l3}` `{r3}` `{options}` `{create}`. A fact that differs by console goes in `byConsole`, or in records limited with `consoles: [...]`. `scripts/check-console-text.mjs` (`npm run check:console`) reads what each console would show and fails on another console's name or buttons.
- **Source console.** A source may carry `console`: `ps5`, `xbox-x`, `xbox-s` or a list of them, set when the page is for those consoles only. No `console` means the source applies to every console. Every source on a playstation.com host is `ps5`; every source on an xbox.com host (support pages and the store listing) is `xbox-x` and `xbox-s`, or just the one whose console page it is. An answer page shows the sources that apply to the chosen console and folds the others under "Other consoles". A record that is `official` for a console has at least one source on an official host that applies to that console. `tests/content/sources.test.mjs` enforces all three.
- **Units.** Sizes are in GB, never bytes or GiB. Jargon is put in plain words where it first appears, for example pre-load (the download before launch) and Safe Mode (a start-up menu with repair tools).

## The spoiler dial

One setting for the whole app: **Off** (the default), **Places**, **Mild**.

- Off shows `none` records only. Places adds `places`. Mild adds `places` and `mild`.
- **Two addresses per hidden page.** The **gate address** (`/places/<id>/`, `/mild/<id>/`, `/places/list/`, plus the tier gates `/places/` and `/mild/`) is what default pages, search results and a typed address reach. It says what kind of content is behind it ("a places page", "a mild gameplay detail") and that the spoiler setting is below it, and holds none of the hidden text: a generic title ("Hidden page"), a generic meta description, no heading, label, link text, related link or og tag taken from the record. The slug in a link is fine. Its Show control is a plain link to the **explicit address** (`/places/<id>/show/`, `/mild/<id>/show/`, `/places/list/show/`), which holds the content in full. The gate also has a Go back to Ask link. With JavaScript and the dial already at or above the tier, the gate forwards to the explicit address (`location.replace`).
- Hidden text is never in a page the default setting loads, nor in a gate page. The build writes each hidden tier to its own files (explicit pages under `/places/**/show/` and `/mild/**/show/`, fragments, a search index and an offline list under `/h/<tier>/`). Default pages, gate pages, the default search index and the offline cache contain none of it. The explicit pages carry no list of the topic's other hidden answers: with script, an empty mount fills from `/h/<tier>/a/` only when the dial allows the tier.
- Tap to show: a `none` answer with hidden details shows one control per tier. Its text is the record's `reveal[].label` when there is one (a generic line written for Off, such as "Show how to keep it safe"; a record that has one is a loss warning, see "The loss-warning rule"), else "Show this detail" with the one-line reason under it, "1 mild detail, hidden until you ask" (the tier stays in the words, so two controls on one page are not the same; never a bare "Show"). It is a real control of at least 48px, a link to the detail's explicit address with `?reveal=1`. JavaScript upgrades it to fetch the fragment in place (with the header `x-lfg-reveal: 1`) and insert it. The dial does not change. A fetch that was redirected is a refusal, never content; the control then follows its link. **Offline (fix round 8):** a tap whose fetch cannot be answered (no network, a failed or non-ok answer) never leaves the page and never lands on the browser's error page: the control stays and a `role=status` line right under it (`src/scripts/offline-note.js`) says "This detail cannot load without a connection. Once you have opened it online, it will work offline." The same line appears in a search result card and on a topic card (the same component), when the dial reaches the tier and the detail cannot load, for a list script fills ("These answers cannot load…", never "nothing here"), for the outside maps ("Outside maps cannot load…"), and as one line under the topic list when the counts cannot load. A hidden page's gate whose dial reaches its tier forwards only when online or when the device already holds the explicit page; otherwise it stays and says "This page cannot load…" under its Show link. Each retries when the connection returns (`online`). A refusal (a redirect) still follows the link. `round8a.spec.mjs` (a), (b), (c) prove it with `context.setOffline(true)` and the worker active. **A revealed detail** has the calm gold rule the answer block uses (`--action`, never the coral error colour) and, inside it, a real 48px **Hide** button (named "Hide this detail") as the first thing in the block, above the text, so nobody scrolls past the detail to find it; the text is set as short paragraphs (`paragraphs()` in `src/lib/answers.ts`: a blank line starts one, and so does every second sentence; one or two sentences stay a single paragraph). Hide removes the text from the page, not just from sight, and brings the "N detail hidden. Show" control back with focus on it. **Lowering the dial** (Mild to Places, to Off) removes every revealed detail from the page at once, without a reload (`reveal.js`, on `lfg:change`), whether the player tapped it open or the dial showed it, and empties any list script filled with hidden answers (`hidden-gate.spec.mjs` checks `document.body.innerText` and the DOM straight after the change). Raising the dial shows what the dial now allows again.
- **Nothing fetches an explicit address ahead of the tap** while the dial is below its tier: no `<link rel=prefetch|prerender|preload|modulepreload>` to a hidden address, no `speculationrules`, no view-transition preloading, no service-worker warming. `check:leak` fails on any.
- **The server backs the dial.** `settings.js` mirrors the dial into the cookie `lfg_dial` (the word `off`, `places` or `mild` and nothing else; `Path=/`, `SameSite=Lax`, `Secure` on https, one year; not HttpOnly, because script writes it) on load and on every change. After the sign-in gate, the middleware refuses every hidden-tier address (explicit pages, `/h/<tier>/**` fragments, search indexes and offline lists) unless the cookie's level reaches the tier, or the request is one explicit reveal: the header `x-lfg-reveal: 1` (the in-place fetch) or `?reveal=1` (the no-script Show link). The marker opens one item (an explicit page or one item's fragment) and never an index, a list or an offline list. A refused request gets a 302 to that item's gate page (an index or list to the tier's gate page) with `x-lfg-redirect: dial` and `no-store`. No cookie counts as Off. The rule is the pure `dialRule()` in `src/lib/gate.js`; `tests/e2e/serve.mjs` applies the same function so Playwright proves the whole flow.
- The Places section opens on a gate that says places are off, with the switch to turn them on. With JavaScript off, the gate is a plain link to the places list's gate address, whose Show link opens the list.
- **The line between Off and Mild** (fix round 3, applied strictly to every record and every `reveal`).
  - **Off holds** the basics: setup, install, account and bonus codes, settings, controls, saving, performance, known problems and fixes, what is and is not in the game at launch, and, where a player could lose something in the game, one generic line (see "The loss-warning rule" below). For a game system Off may say only that it exists and that its details sit behind the Mild setting, in one sentence, or say nothing.
  - **Mild holds** how a game system works in play: named in-game apps and services, prices and fees, how selling or stealing works, how police respond and how to shake them, how stats rise, and anything a press guide learned by playing rather than Rockstar stating it before launch.
  - **Places** is where things are.
  - A `none` record that is mostly Mild material becomes a short Off line plus a Mild `reveal`, or moves to the `mild` tier whole. A hidden record cannot be in Most asked: ranks 1 to 20 stay on Off records, each used once. An Off answer never ends on a tease that hints at the hidden part ("there is a clever way..."); the pointer is plain ("its details sit behind the Mild setting"). Where a source's own title or address would give the hidden gist away, the record moves to Mild whole, so the source link is hidden with it.
  - **The loss-warning rule (fix round 5, settled by the owner; it replaces the fix-round-4 rule that put "bank it" at Off).** Two reviewers pulled opposite ways, one wanting the remedy at Off and one finding that the remedy states how money works. The rule: at Off a loss warning says **only that a loss is possible, in generic words that state no game rule**: exactly `You can lose in-game money. There is a simple way to keep it safe.` (fix round 7; any other in-game loss uses the same shape, `You can lose in-game <thing>. There is a simple way to keep it safe.`). The second sentence says there is a way, and states no rule. The sentence is directly followed by one control, **"Show how to keep it safe"**, an ordinary one-item reveal of a Mild detail (`reveal[].label`; the dial stays at Off). **The one rule for "carries a loss warning": a record with a `reveal[]` item that has a `label`.** The search index marks such a record (`loss: { tier, label }` in `search/none.json`, Off-safe words only), the card and the answer page read the same field, and no string match on the text is used anywhere. **The control is the primary button**, the same filled style as Done (`--action` fill, `--bg` text, 48px, no dashed edge, no pill), at the full width of its container, never a collapsed-disclosure look: it is the next thing to tap. **Where the pair appears (fix round 7, item 1):** on the answer page the button is the element directly after the warning (`.answer__a + .reveal--warn`), before the body; on a topic or cheat-sheet card it is under the card's text; and a search result that carries a loss warning is a card (`li.ask-loss`) holding the answer link (question and warning) and the button, 8px apart, so it never ends on the warning alone. The reveal opens in place in all three (the same fetch with `x-lfg-reveal: 1`, `reveal.js` serving the dynamically built search card too), the dial stays Off, and Hide puts it away. At Mild the search card keeps the button (a tap still opens it in place). The rule itself (what is lost, when, and how to avoid it) lives in that Mild detail, which names its own sources. It is applied to every record, and so to Ask, a cheat sheet, the search data and the snippets a search shows for "money", "cash" and "car": each shows only the generic line.
    - **Real-world losses are different and stay fully visible at Off.** Losing save data, progress or purchases through a console action (uninstalling, deleting, reinstalling, switching accounts) is setup, not a game rule. Any line that tells a player to delete, uninstall or reinstall (a summary, a per-console line, a step) carries the save warning in that same line, or links `/a/will-i-lose-anything/` in it, and the PlayStation and Xbox steps stay in the visible text.
    - **One plain sentence, on About and beside the dial:** "Off names a game system only to say it exists; where you could lose something, Off says so and one tap shows how to avoid it."
    - **Tests.** `tests/content/loss.test.mjs`: no Off record shows a game-rule word (carried or carried cash, bank, ATM, die or death, loot, deposit, cash or loot dropped; "drop" beside none of those, such as a frame-rate drop, is fine), no sentence of a Mild detail is in an Off record, the money-loss sentence is exactly the generic line in the record's short and every per-console line, each such record has the Mild reveal with the label above (and the whole two-sentence line ends every headline and body line that warns), and a delete, uninstall or reinstall line also carries the save warning; each check is proved by planted sentences. `tests/leak/loss-leak.test.mjs` reads the real build: no sentence of the detail is in any Off page or Off search file, the search rows for the two records end on the generic line and carry the `loss` marker (and no other row does), and no Off answer, topic or Ask page holds a rule word. `tests/content/tiers.test.mjs` (`lossWithoutRemedy`) still fails any other Off loss warning that has no remedy; only the generic line is exempt, because its remedy is the control.
  - Fix round 3 moved four records whole to Mild (`fast-travel`, `stolen-cars`, `wanted-and-police`, `core-stats`; they left Most asked and the core-stats checklist step went with them) and cut `keep-your-cash` to one warning line plus a Mild detail.
- **The one-line wording** beside the dial and in the settings sheet is exactly: Off: "the basics: setup, settings, controls, saving, fixes"; Places: "adds where things are"; Mild: "adds how the game's systems work in play". The About page spells the rule out in plain words, with a generic example for each (the Mild example names no hidden detail).
- **How the line is tested** (`tests/content/tiers.test.mjs`). `tests/content/tier-rubric.json` lists every record and every `reveal` with its tier and a one-line reason from the rule, and the test fails when the file and the records disagree. Each Off record also says which part of the Off list it holds (`holds`). The test holds a list of Mild signal words (unlocks later, secret, cheat, glitch, trick, ways to shake the police and similar) and a list of game-system specifics: named or described in-game apps and services, prices and fees (a currency symbol and a number, "fee", "fare", "costs"), where cash or loot is deposited or sold, how police respond (wanted levels, police remembering or searching), and how stats rise. It fails when the visible default text of a `none` record, source titles included, holds one. It also fails when an Off answer ends on a tease, when a `none` record cites a play-guide source (GameSpot, IGGM, Crime Net Gazette, Vice Atlas: pages written from playing or a hands-on preview) with no `pressGuide` line in the rubric saying why that is fine, and when a hidden record has a `rank`. Planted sentences, including those a reviewer found at Off, must be caught. Changing a tier means changing the rubric in the same commit.
- The dial is on the first screen at every width, in the header.

## Console

One stored setting, `console`: `ps5`, `xbox-x` or `xbox-s`. It is saved on the device like the dial (see "Saved on the device"). **Never chosen is a state of its own**: the key is absent, `settings.js` hands the page `console: ''`, and `<html data-console>` is not set.

- **One name per console, everywhere.** `PS5`, `Xbox Series X`, `Xbox Series S`, from one list (`src/data/consoles.js`). Where space is tight (the header chip, the console prompt, the sheet's radios, an answer's console switch) the visible text is the short form, `PS5`, `Series X`, `Series S`, and the full name is still read out and copied (`ConsoleName.astro` puts `Xbox ` in a screen-reader-only span in front). Sentences, notes, fold summaries and aria labels use the full name. `Xbox X` and `Xbox S` are never used, anywhere; `consoles.spec.mjs` scans all text and every attribute of every page, in every console state, and fails on either.
- **First run.** Search comes first on the Ask screen. Under it, in the place "Next up" takes once a console is chosen (see "Screens"), sits a slim prompt, "Which console do you play on?", with one row of three 48px buttons (PS5, Series X, Series S; the accessible names are PS5, Xbox Series X, Xbox Series S). It is not a card and does not push the search off the first screen at any width. Choosing saves the console, hides the prompt (CSS: `html[data-console] .console-card`), shows Next up and moves focus to the screen heading. The prompt needs script; without it it is not shown, and the Next up strip shows its every-console steps.
- **Always visible.** The header chip names the console in use on every screen: the short value alone ("PS5", "Series X", "Series S"; "Pick console" until one is chosen). Its accessible name is the full one, "Console: Xbox Series X, change" ("Pick console, change" before a choice, so the visible words sit whole inside the name), set as an `aria-label` by `settings.js` because CSS cannot change one. It has no visible "Console" word: axe wants a button's visible text to sit whole inside its name, and a label would split "Xbox Series X". The chip opens the settings sheet, where it can be changed. The spoiler chip shows the level word in `--accent` when the level is Places or Mild (Off keeps the text colour; AA on the chip in both themes), so a raised level shows at a glance (fix round 8). No chip text wraps at any width from 320px up, also at 130% text (under 400px the chips' side padding is 4px so "Pick console" and "Spoilers: Places" fit): the header is one row and as tall at 320 as at 390 (`consoles.spec.mjs`). Answer pages that have `byConsole` text also keep their own switch.
- **Which records show.** A record with `consoles: 'all'` is console-neutral: its text names no console, and where consoles differ it uses `byConsole` text or button tokens (`{cross}`, `{circle}`, ...). A record with `consoles: ['ps5']` (or `['xbox-x', 'xbox-s']`) is only for those consoles. It shows in its list for them (`data-only="ps5"` on the row, CSS from `styles/console.css`). For any other state, a never-chosen console included, it is hidden there and its title is one plain link in that list's **Other consoles** fold, a native closed `<details>` (`OtherConsoles.astro`, copies marked `data-other`). Nothing in the fold is a tick box or repeats an id.
- **Never chosen.** Treated as "no console matches": only `consoles: 'all'` records show, the console-only ones wait in the fold, `byConsole` is not used (the base text shows) and a button name shows both consoles' labels with a spaced slash that is real text (`✕ / A`, `L3 / LS`), on pages and in search results alike, never glued (`✕A`, `L3LS`). The prompt under the search is the calm prompt; there is nothing else to dismiss.
- **Sources for a console.** A source may carry `console` (one console or a list). On an answer page the sources block shows the sources with no `console` and the ones for the stored console (all of them while no console is chosen). The others sit in a native, closed `<details>` named "Other consoles" inside the same block, so a link is never hidden for good. CSS decides (`console.css`, `data-src-for`, `data-src-other`), so it needs no script; a block with no console-tagged source has no fold.
- **Where it applies.** Everywhere answers are listed: Ask (Most asked rows, stage to-dos), Checklist, topic cheat sheets, the answer page's related list and the desktop list column. Most asked and the lists inside hidden tiers are only filtered, with no fold.
- **Counts.** Progress counts only the to-dos that show for the console (`src/lib/console.js` `applies()`, used by `home-todos.js` and `checklist.js`). A tick on a to-do for another console stays saved and is not counted.
- **One order.** The Ask screen and the Checklist list to-dos in the same order, from one function, `todosOf()` in `src/lib/answers.ts`: most asked (`rank`) first, then by id. A to-do may carry `order` (a positive whole number, lower first), set where one step must wait for another; it wins over `rank`, and to-dos with no `order` follow in `rank` order. "Before you start" runs: redeem the boxed-copy code, update the console, free the space, turn on automatic downloads, check the countdown (`tests/content/fixes.test.mjs`).
- **A page for another console.** A page whose `consoles` is a list without the stored console (for example `/a/ps5-system-update/` opened by an Xbox player) leads with one line, "This page is for PS5, not Xbox Series X", which is the page's heading while the rest is folded, and one link to the page for their console: the record with the same `topic`, a `consoles` list that holds their console and the most question and keyword words in common (`counterpart()` in `src/lib/otherconsole.js`, built into the page), else that topic's cheat sheet. The rest of the page sits in a native `<details class="other-fold">` ("Show the PS5 version"), open in the HTML and closed by `other-console.js` only while the stored console does not match; the line, the link and the summary show only then (`console.css`). A never-chosen console, a matching console and an every-console page are unchanged.
- **Test fixtures.** `tests/fixtures/answers` has a PS5-only and an Xbox-only record with a to-do each. After choosing a console the visible text of Ask, Topics, a cheat sheet, an answer and the Checklist names no other console outside the fold, and button names are that console's (`behaviour.spec.mjs`).

## Screens

| Route | Screen | Content |
| --- | --- | --- |
| `/` | Ask | The title with one line under it saying what the guide is for and what the spoiler setting is now, which follows the dial with CSS (`.by-dial`, shown by `html[data-dial]`): Off says spoilers stay off until turned on; Places and Mild say spoilers are on at that level and what it adds (it names no console; no line anywhere says spoilers are off while the level is raised, `round8d.spec.mjs`), the search box, then **Next up** (below), "Most asked" (top 8 by `rank`), then "Your stage": the stage picker and that stage's to-dos. **The fold (fix round 6).** Once a console is chosen the full list is not shown a second time under Next up: the stage picker stays, and the to-dos sit behind one native `<details>` row, "See all N steps" (a 48px raised row ending on a chevron that turns down while open; N is the number of steps of the stored stage that fit the console, redrawn by `home-todos.js` when a tick, the stage or the console changes). It is closed when a console is chosen; opening or closing it is the player's and stays through ticks and stage changes, and it closes again only when a console becomes chosen. Before a console is chosen, and without script, the `<details>` is open and the row is hidden, so nothing changes and the no-script floor shows everything (`round6b.spec.mjs`; an inline line after the row sets the first state before paint, so nothing shifts). **Next up** is a compact strip under the search: the next one or two unticked steps of the player's stage (the stored stage, `before` by default) that fit their console, each a whole-row 48px link to its answer, drawn as the Most asked rows are (a raised `--surface` row with a `--line` border, the pressed state, and the arrow the checklist rows end on at its end, so it reads as something to tap in both themes: `round5.spec.mjs`), and a progress count ("2 of 6 done", of that stage and console) that links to the Checklist. Before a console is chosen the slim console prompt (see "Console") takes its place, and once one is chosen the prompt goes and the strip shows. It redraws from the stage lists below it whenever a tick, the stage or the console changes (and on each visit); with every step ticked it says so and still links the Checklist. Without script it shows the first two steps of `before` that fit every console, with a "See the checklist" link. The first screen stays light: the header, the search, Next up, then Most asked (`nextup.spec.mjs`). A to-do row is the tick row plus a chevron to its answer, 16px apart |

## Touch

The app is used mostly by touch, on a phone or tablet. Every screen holds to these rules, and later work reuses the shared tokens (`--tap`, `--gap-tap`, `--safe-*`, `--text-input`) and classes (`.tap-list`, `.seg`) in `tokens.css` and `global.css`.

- Every tappable thing is at least 48 by 48 CSS px (`--tap`), with at least 8px (`--gap-tap`) between neighbours. The one exemption: a link inside a sentence of running text in an answer body or a text page (`.prose`: an inline link with more text around it than the link). A link that is the whole line, or a list item, is not in a sentence and holds to the rule. No other exemption exists.
- The whole row is the target, not a small link inside it. A checklist row is one label of at least 48px with an 8px gap to the next row; the tick box is only its picture. **The 8px is the list's own `gap`, real dead space, never margin inside a row's label or link** (fix round 6): every stacked list of tappable rows (`.tap-list`, the Topics rows, cheat-sheet cards, the Checklist and Ask to-do rows, Next up, search results, source lists, the "Other consoles" folds) has `row-gap: var(--gap-tap)` and its links and labels carry no vertical margin; the hairline between plain rows sits in the middle of the gap (a pseudo-element on the row above it). `round6.spec.mjs` reads the computed row gap and the margins of every list on the main screens. A card's stretched link covers the card's content, and the reveal control sits 8px or more below it. A to-do row's chevron is its own 48px target with 16px between it and the tick row; that space belongs to neither (`ui2.spec.mjs` walks it with `elementFromPoint`). Touch screens still snap a tap that lands a few pixels off a control to the nearer one, so the gap is the margin for a thumb, not a dead zone.
- **How it is tested** (`touch.spec.mjs` for the main screens and the open sheet, and `touch-all.spec.mjs` for every page the build writes, from one list in `helpers.mjs` that a test keeps equal to the build: Ask, Topics and every cheat sheet, every answer with its body and sources, Checklist, New, About, the gates and explicit pages of both hidden tiers, and the 404; at 320, 390 and 820 wide with touch, first-run and everything shown with every fold open): for every `a[href]`, button, `summary`, input, select, textarea and `[tabindex]` (a `tabindex="-1"` focus target is not a control) the test samples the page with `elementFromPoint` (to the pixel at the edges) and keeps the points where a tap reaches that element, itself, a child, its label or a link stretched over a card. The hit area is the bounding box of those points, so a 24px box inside a bigger label is judged as the label, and a control another element covers is judged as what is left. Nothing is skipped for being part of something bigger. **Neighbours in one list also get a dead-space check** (fix round 6): for every pair of controls in the same list or stack (the same `li` parent, or the same parent for loose controls) whose hit areas sit one beside or above the other, the midpoint of the gap between the two hit areas is sampled with `elementFromPoint`, and a tap there must not activate either control, on every page at 320, 390 and 820. A self-check plants two 48px rows at 0px (flagged twice: hit areas 0px apart, and the midpoint activates a row) and the same rows with an 8px list gap (must pass). **Why the earlier check missed it:** it measured the clearance between hit areas, and the 8px was margin on each label, so the labels were 8px apart on paper while the page showed rows with only a hairline between them and a thumb saw them touch. The check now holds the space itself (the list gap) and the middle of it. Under 48px either way fails; so does another control's hit area closer than 8px (judged by the tappable points). **A link, button or summary must also be 48px in its own box** (`getBoundingClientRect`), not only in its tap area: the cheat-sheet question links are stretched over their card, so a tap always reached 48px or more and the first version of the test passed them, while a reviewer, Lighthouse or voice control reading the box saw a bare 20px line. Those links now carry their own 48px (`AnswerCard.css`, `--q-pad`). Inputs are judged by the tap alone: a 24px tick box inside a 48px label is the label's target. Fixed and sticky layers float over the page and are compared only within themselves, and what an open sheet covers is not judged until it closes. A self-check feeds the measure a 24px box in a 30px label, touching rows, a bare 24px link and a 20px link stretched over a card, and needs it to flag all four. `touch-report.mjs` prints the smallest hit area per screen and width.
- The tab bar sits at the bottom on phones. Leave clear space around the spoiler dial and the reveal controls.
- Respect the safe-area insets in both orientations: `viewport-fit=cover` and `env(safe-area-inset-*)` on the header, bars, rail, content and footer.
- Nothing depends on hover, long-press, double-tap, drag or swipe. Every `:hover` rule lives under `@media (hover: hover) and (pointer: fine)` (a touch screen has no hover to get stuck on; `round8d.spec.mjs` reads every page's CSS and fails a `:hover` rule outside it). A link inside running text (a paragraph, a definition or a list item of prose) is at least 24px tall to hit, also at 130% text (WCAG 2.5.8): `padding-block: 0.15em` grows the box, not the line. Taps show a pressed state with `:active`, and `touch-action: manipulation` removes the double-tap delay.
- Text inputs are 16px or larger. Body text is 17px or larger.
- No layout shift on a state change: a selected control changes fill or colour, never size or weight.
- `overscroll-behavior-y: contain` on the page, so pulling down does not fight a refresh.

## Saved on the device

One `localStorage` key, `lfg:v1`, holding the v2 state:

```ts
type State = {
  v: 2;
  settings: { [K in 'console' | 'dial' | 'theme' | 'stage']?: { value: string; at: number } };
  items: { [id: string]: { done: boolean; at: number } };   // id = an answer id; done:false is an untick
};
```

`at` is a millisecond timestamp, set when that setting or tick last changed. Saving is local first and works offline. The state is read and written only through `src/scripts/settings.js`, which hands the rest of the code the flat shape `{ console, dial, theme, stage, done: string[] }`.

- **Settings stay on the device.** The spoiler dial, console, theme and stage are never sent to the server and never read from it or from an import code. Nothing from `/api/progress` can change a setting (`absorb()` takes ticks only and drops any `settings` it is handed). A new device starts with the dial at Off, the console on PS5, the theme on the device setting and the stage at the start. Changing a setting never starts a sync.
- **Old shape.** Before synced progress the value was `{ console, dial, theme, stage, done: string[] }`. It is still read and keeps its settings and ticks on this device. On first load it is stored as v2 with every old value at time 0, so nothing is dropped.
- **Export code.** Ticks only: `{ v: 3, items }` as JSON, base64url, no setting inside. Import validates before it writes, accepts a v3 code, an older v2 code or an old-shape code, keeps only the ticks and merges them into this device (see "Synced progress") and then says "Ticks from the code are now on this device.". The settings of an old code are ignored: the player chooses the dial on each device. It does not replace what is already here. The Checklist's line about the code says what it is (text that holds the ticks only) and that copying it sends it nowhere by itself.
- **What leaves the device.** Only the ticks, sent to the owner's own private blob behind the password gate (see "Synced progress"). Nothing else: no analytics, no third party.
- **What the site really stores** (every sentence on About and the Checklist about this is checked against it, one test per sentence group in `sync.spec.mjs`). Cookies: the sign-in cookie `lfg_gate` (set by the gate on the live site, `HttpOnly`) and `lfg_dial`, the word `off`, `places` or `mild`, host-only, sent only to this site, used only so the server can refuse hidden pages below the dial. **About says it in one sentence** (fix round 6: it used to say only that the setting stays on the device, while the level also travels as this cookie): "Your spoiler setting stays on this device, and its level is also sent to this site in that cookie so the server can refuse hidden pages; the server reads it on each request and keeps nothing, so it is not stored there or tied to a person." It is true because the middleware reads the cookie per request, keeps no state and logs nothing about it, and the online copy never receives it (`sync.spec.mjs`). The sync paragraph says the spoiler setting, console, theme and stage are never copied to the store. `localStorage`: the one key `lfg:v1`, holding settings and ticks; no `sessionStorage`, no IndexedDB. The service worker's cache: a copy of the guide's pages so they read offline; lowering the dial removes the hidden tiers from it. What syncing sends: ticks only. Every request a page makes goes to this site (no analytics, ads or third party). The code is text: showing, selecting or copying it makes no request. The pages never say the code or the ticks "stay on this device" as a design rule, and never say "saved on this device only" unless syncing is not available (see "Synced progress", Status line).
- **Lowering the dial clears the device.** When the dial goes down (Mild to Places, Places to Off, Mild to Off) the page tells the service worker which hidden tiers are still on, and the worker deletes every other tier's files from its cache: `/places/**`, `/mild/**` and `/h/<tier>/**`, with that tier's cache mark. Turning a tier on caches it again as before (see "Offline and install").

## Synced progress

Only checklist ticks follow the owner across phone, tablet and desktop. Settings do not (see "Saved on the device"). Local first: the page works, and every change is saved, with no network at all.

- **One function, one blob.** `api/progress.ts` is a Vercel Function (default export `{ fetch }`, Node.js runtime). It keeps one private Vercel Blob at `progress/ticks.json`, in the store `leonida-progress`, using `@vercel/blob` on the server only. The store's token is the Vercel env var `BLOB_READ_WRITE_TOKEN` (production, preview and development); it never appears in the repo, a commit, a log or a test. Nothing is added to the browser bundle.
- **The old record is abandoned.** `progress/state.json` held every device's settings and is never read again. The function makes a best-effort, one-off `del()` of that pathname (once per instance, never failing a request); the code is marked `shortcut:` and is removed once the old blob is gone.
- **Behind the gate.** The route is `/api/progress`. The middleware skips this one path (see "Access gate"), so the function checks the gate cookie itself. The function adds no auth, cookie, user id, database or sync library.
- **GET** returns the saved ticks, or the empty record if there is none or the stored blob is not the ticks shape. **PUT** takes ticks, merges them into the saved ones, stores the result only if it changed, and returns it. Any other method is 405.
- **Shape (v3).** `{ v: 3, items: { [id]: { done: boolean, at: number } } }` and nothing else.
- **Checked at the boundary.** The body must be JSON (`content-type: application/json`), at most 64 KB, exactly the v3 shape: ids that are slugs of at most 64 characters, at most 300 items, whole-number times. A body with a `settings` key (the old v2 shape included) or any unknown field is 400 (413 when too large). The error body never carries storage detail.
- **Merge** (`src/lib/merge.js`, plain JS, shared by the browser and the function). Per item the newer `at` wins. A tie keeps a tick over an untick. It is idempotent, commutative and associative, so devices can sync in any order and two devices that tick different things offline both keep their ticks.
- **No lock.** Read, merge, write. Two PUTs at the same moment can lose one update, and the next sync of the loser puts it back, because merge is idempotent and commutative.
- **Client** (`src/scripts/sync.js`). **Read first.** On page load (and on the `online` event and each retry) it GETs the saved ticks, merges them into the device and sends a PUT only when the merged result differs from what the server returned, so a page load with nothing changed sends no write. About 400 ms after a tick changes (or an import) it PUTs the ticks straight away, once, and merges the answer's ticks into the device. Any `settings` in an answer (an old server) are dropped. A tick made on this device always gets a time later than what it replaced, even on a slow clock. On failure it retries quietly (the `online` event, the next change, then backoff up to five tries) and never blocks the page or shows a dialog. A missing or failing endpoint (JavaScript off, offline, 401, 5xx) leaves the page fully working on local data.
- **Offline cache.** `/api/` is network-only in `public/sw.js`; progress is never served from the cache.
- **Status line.** The Checklist shows one calm line in one `role="status"` region (`[data-sync]`), about ticks only, in one of three states, each exactly what is happening:
  1. Synced, after the last attempt succeeded: "Copied online (synced) at <time>: your ticks are saved on this device and in this site's private store."
  2. Not syncing right now (offline, signed out, a 5xx, a bad answer): "Not syncing right now. Your ticks are saved on this device. We will try again." (fix round 7: three reviewers could not follow "Could not reach the online store (the sync service)"; the words "sync service", "sync store" and "online store" are not used anywhere, on a page, in a script or in a test). "We will try again" is true: the retries above (the `online` event, the next change or load, then backoff) are the retry, and `sync.spec.mjs` ("a tick made in one browser appears in a second after reload") has the server come back and the tick arrive with no action from the player.
  3. Syncing not available (no sync endpoint on this build: the read gets 404 or 405; script off): "Syncing is not available here. Your ticks are saved on this device only." No retry for a missing endpoint. All three sentences are plain and short, say what is true of the ticks on this device, and carry the plain words for sync in the same sentence (see "Plain words as a checked rule").
  The line is in the HTML as state 3, so it holds without script. While script runs and the store has not answered yet the line is hidden (`visibility`, with its room kept so the page does not jump): no claim either way. It never says synced when the last attempt failed. A stub of `/api/progress` answering 200, 500, abort, 404 and never, and a script-off page, test each state; a page load with nothing changed sends one GET and no PUT, and one tick sends exactly one PUT (`sync.spec.mjs`).
- **Known limits.** Last write wins per tick, by clock: a device whose clock is far ahead will win ties it should not.

## Access gate

While the site is private, a Vercel Routing Middleware (`middleware.ts` at the repo root, with the pure `decide()` in `src/lib/gate.js`, plain JS so the platform's bundler can trace it) stands in front of every page and asset. Output stays static Astro; no adapter, no runtime dependency, nothing added to the browser.

- **Password.** The Vercel env var `SITE_PASSWORD` (production and preview). It never appears in the repo, a commit, a log or a test. If it is unset or empty, the gate answers 503 to everything: closed, never open.
- **No valid cookie.** A small login page (status in the next item): inline styles from the tokens in both themes, one labelled password field (16px or more), one big button, 48px targets, `no-store`, `noindex`, and a CSP that allows no script. Posting the right password sets the cookie and answers 303 to the page first asked for. Only a same-origin path is followed (a path starting `//` or `/\` goes to `/`). The page says three things, in order: the name, "This guide is private for now. Enter the password to open it." and "An unofficial, spoiler-safe companion guide for the game." (fix round 8: so a person who lands there knows what the site is; the page is otherwise unchanged). A wrong password re-shows the page with one plain error line, which has `role="alert"` (a screen reader announces it) and the field takes focus with `aria-invalid` and `aria-describedby` on that line (`tests/gate/gate.test.js`).
- **Login page status.** The login page and its wrong-password page are a document response, and browsers log every 401 document in the console. So when the request is a page navigation (`Sec-Fetch-Dest: document`) the gate answers them 200 with `cache-control: no-store`; every login page carries `x-lfg-gate: login`. Every other request (assets, JSON, fetches, curl without that header) keeps 401, so no content ever leaks. A real browser with the cookie sees no error on `/` or `/checklist/`.
- **Service worker.** The worker never stores a response that carries `x-lfg-gate` or `x-lfg-redirect`, or one that was redirected (a hidden address sent to a 200 gate page), so a cached login or gate page can never replace a real page offline. Items already cached while their tier was on stay readable offline; lowering the dial removes them (see "Saved on the device").
- **Spoiler dial rule.** After a request passes the sign-in decision, `dialRule()` (`src/lib/gate.js`, pure) decides the hidden-tier addresses by the `lfg_dial` cookie; see "The spoiler dial". Paths are decoded once, backslashes read as slashes, dot segments resolved and case folded before the rule looks, so `/places/../`, encoded dots and `//` cannot get round it. Anything deeper than a gate page under a tier is treated as hidden. It adds no state: the cookie is a copy of a setting the player already holds on the device, used for nothing else and sent only to this site.
- **Cookie.** `lfg_gate` holds SHA-256 of the password plus a fixed salt, never the password. `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age` one year. Compared in constant time. It is a gate token, not an account and not tracking, and it holds no preference: "No accounts" and the `lfg:v1` shape do not change. The only other cookie is `lfg_dial` (see "Spoiler dial rule" above): the level word, readable by script.
- **Open to everyone.** `/manifest.webmanifest`, `/icons/**` and `/favicon.svg`, so the app can be installed (a manifest is fetched without cookies). Nothing with content is open: `/search/**`, `/h/**`, `/places/**` and `/mild/**` stay behind the gate (and, signed in, the hidden tiers behind the dial rule). `/sw.js` stays gated too: browsers send cookies when they fetch it, and only a page that got through registers it.
- **Offline.** The gate runs only on the network. Pages a signed-in device already cached stay readable offline.
- **Rotate.** Change `SITE_PASSWORD` and redeploy; every old cookie stops working.
- **Tests.** `npm run test:unit` runs `node:test` over `tests/**` with invented passwords and no network. Run against the live site only by the build orchestrator.
- **Progress sync.** `/api/progress` is a Vercel Function behind this gate (see "Synced progress"). Its Blob token is a separate env var and is never read by the gate.

## Search

Players type plain sentences, so search is forgiving. No search library: `src/scripts/search-match.js` is pure (no DOM) and a test imports it.

- **Index.** A build step writes `/search/none.json` and one index per hidden tier under `/h/<tier>/search.json`. Each row has `id`, `question`, `short`, `topic`, `consoles`, `rank`, `forConsoles` (the consoles the record speaks to: its `consoles` list, the consoles it has `byConsole` text for and the consoles its sources are tagged for, built by `forConsoles()` in `search-match.js`; it holds no hidden text) and, when the record has them, `keywords`. The client loads only the indexes the dial allows. A result opens `/a/<id>/` (none) or `/<tier>/<id>/`.
- **Words.** The query is lower-cased and split. One list of filler words (`STOP` in `search-match.js`) is dropped: how, do, i, my, the, a, is, on, what, are, will, it, does, get, want, need, play, game, fast, too, best, keep, same and similar. A **meaningful** word is a non-filler word of three letters or more, or a number of two digits or more, or one of a few real two-letter terms (pc, gb, tb, hz, tv, hd). Plurals and endings (-s, -ies, -ing, -ed, a doubled last letter, a trailing e) fold to one stem. A numbered size such as `512gb` is `512` and `gb`.
- **Typos.** One typo is tolerated: a letter more, fewer or different when both stems have five letters or more (so cash is not crash), and two neighbouring letters swapped (optimal string alignment distance 1) from four typed letters ("svae" is save). The last word may be unfinished: it matches the start of a word.
- **Synonyms.** `ps5`, `ps` and `playstation` are one word. `xbox`, `series`, `xsx` and `xss` are one word. `storage`, `space`, `drive`, `disk`, `ssd`, `hdd`, `gb`, `tb` and `gigabyte` are one word. `not`, `doesnt`, `dont`, `cant`, `wont`, `isnt`, `didnt`, `cannot` and `never` are one word, so "does not work" can meet a keyword "doesnt work". A console word or a no says what the player owns or colours the question: it is not the thing asked, so it counts for less and never makes an answer by itself.
- **Strong and weak matches.** A word is found in the question (weight 4), `keywords` (3), `short` (2) or the topic name (1). A hit in the question or the keywords is **strong**; a hit in `short` or the topic name only is **weak**. A word found in several fields counts for more (the weights add). A keyword phrase whose meaningful words are all in the query (such as "update before play") breaks ties.
- **Generic words.** A few words are so common in questions that matching one alone is no answer: mode, change, work, problem, issue, help, time, new, open, first, last, tonight, today, now, before, after, console, version (`GENERIC`). They rank an answer but never make one, and they do not count when judging how much of the question matched.
- **Answers.** A record is a confident answer when a meaningful, non-generic word of the question matches its question or keywords (strong), and the record holds at least half of the query's informative words (all of them, including a word that appears in no answer: "how do i unlock the secret car" has three, and an answer about unlock times holds one, so it is no answer). A hit in the short text or the topic name alone is never a match; a query made only of one topic's name is the one exception, below. A query made only of one topic's name ("money", "settings") lists that topic: a topic hit is strong for it. Answers are ordered by strong matches, then all words matched (console words and the no-word count 0.3), then a whole keyword phrase, then the weights with rarer words worth more, then `rank`. The list is cut at five; a "Show more" button (a real `<button>`, 48px, under the list) shows the rest, and focus moves to the first answer it revealed. A new question starts cut again. The status line above says how many answers there are.
- **No answer.** The owner's rule: a real match is a meaningful word of the question found in a record's question or keywords, on at least half of the informative words (see Answers). When no record is a real match the page shows the status line "This guide has no answer for that yet." and one row, "Browse all topics", that opens `/topics/`, and nothing else. There is no "Possibly related" list or heading, no weak card, no most-asked fallback: the matcher returns only `found`. The same holds under the where-is note (an unrelated card never follows the places note); cards follow it only when a real match exists. There is no line about answers behind a spoiler setting and no settings button, because a player read such a line as a hint that story answers exist (`search.spec.mjs`, `round4.spec.mjs`). "how do i get a million dollars fast", "my kid wants to play too", "how do i unlock the secret car" and "where is the nearest gun shop in the city" all reach this, and each is a `NONE` row in the question table and a Playwright test that asserts no card renders. It is never a dead end: the Topics row is always there (except under a known-problems query, where the known-problems row is the way on).
- **The question table.** `tests/search/questions.json` holds more than 180 questions written the way players talk, including every question the reviewers typed in three rounds, typos, plurals, filler-heavy sentences, Series S, PS5 and Xbox phrasings and more than 30 the guide cannot answer at the default setting. Each row names the answer id that must come first (or a list any of which may), or `NONE`: no confident answer. A row may carry `console` (default `ps5`), `dial` (`off` by default, `places` or `mild`: the tiers the page would load, so an answer that sits behind Mild is `NONE` at Off and a row at `mild` names the answer) and `pending`, a reason it fails until content lands; a pending row that starts passing fails the run. `scripts/check-search-questions.mjs` (`npm run check:search`, in `npm run check`) runs the table through the real matcher over the real answers, filtered by console like the page, and lists each wrong question with what it got. The same table runs as a unit test. New gaps a reviewer finds go in the table first.
- **Natural questions.** "do I need to download a patch before I play" finds the day-one patch answer: the answer's `keywords` hold the words players use (patch, update before play, launch update). Keywords are folded the same way as the query, so filler inside a keyword phrase does not matter.

## Offline and install

A hand-written service worker and a web app manifest. On install it caches the pages and assets listed in a build-generated list of default-tier URLs. Hidden-tier files are cached only after the player turns that tier on. The New screen shows "Works offline" once the cache is ready.

**Hidden details offline (fix round 8).** A tap on a show control (the player's explicit one-item reveal, header `x-lfg-reveal`) that is answered online puts that one fragment (`/h/<tier>/a/<id>/` only, never an index or a list, never a redirected or refused answer) in the worker's cache; a later offline tap, after a reload too, opens it from there (the cache match ignores the header and `Vary`). The worker keeps such a fragment while the dial stays or goes up; **any lowering of the dial** (the page tells the worker with `lowered: true`) deletes every hidden tier that is off now, these fragments included, and a tier cached whole is dropped as before. A page load at Off removes nothing. A document navigation offline to a hidden address (`/places/**`, `/mild/**`, `/h/**`) the device does not hold gets a tiny 503 page ("Not available offline", one sentence, a 48px link back to Ask, no text from any record) instead of the browser's error page; held hidden pages are served as before. A statement about an outside site names its source and the date checked (`avoid-spoilers`: "GTA Intel (checked 19 November) says ...").
- **Control schemes.** The one source (Insider Gaming) names face buttons with PlayStation names only. The Xbox text says plainly that the face buttons (A, B, X, Y) are unconfirmed and does not translate; it gives the stick, trigger and bumper mappings that source names.
- **Launch day has come.** Steps and questions that only made sense before launch are reworded ('Check the game is ready to play on your console', not the countdown). `checked` is the real current date.
- **Numbers.** Where a cited source gives a figure that answers the question, the answer states it and names the source: the frame-rate answer carries Digital Foundry's measured dips and input lag.
- **Plain words as a checked rule (fix round 6).** `src/data/jargon.js` is the one list: one object per term (`term`, `forms`, `means`, `plain`), 19 terms: pre-load, licence, sync and synced, cross-progression, Optimized for Series X|S, Storage Expansion Card, internal SSD, hard save, PSSR, power cycle, region-locked, cloud saves, HDR, ray tracing, temporal upscaling, FSR, infostealers, reticle and haptic feedback. On a page, in a script's strings or in a record text, the first use of a listed term has its plain words in the same sentence, before it or after it ("saves copied online (synced)", "downloading before launch (pre-load)"); otherwise the term is not used. `scripts/check-plain-words.mjs` (`npm run check:plain-words`, in `npm run check` and `npm run check:content`) reads every built HTML page (a source link's own title stays as written, so outside links are not read), every string in `src/scripts/*.js` and each text of each record on its own, and fails naming the page, the term and the sentence. Add a term by adding one object. Unit-tested with planted violations and a passing sample (`tests/content/plain-words.test.mjs`). The first run found and fixed: HDR (the question and the checklist step), sync and synced (the three Checklist status lines now read "Copied online (synced) at ...", "Not syncing right now..." and "Syncing is not available here..."), pre-load (day-one patches), internal SSD (Make room, Xbox), hard save (how to save) and Storage Expansion Card (Series S space).
- **Plain words (round 5 adds licence, sync, region-locked, cloud saves, HDR and the page title word pre-load).** "your right to play (your licence)", "copied online (synced)", "limited to one country (region-locked)", "saves kept online (cloud saves)", "HDR (extra-bright picture)". A record whose source title says pre-load (the page's own title, which stays as written) says in its own words that it means downloading the game before launch (`fixes.test.mjs`). A term a non-gamer may not know comes second, after a plain phrase: "a sharpening boost (PSSR)", not "PSSR"; "switch it fully off and on again (a power cycle)"; "downloading before launch (pre-load)"; "progress shared between consoles (cross-progression)"; "the store label is Optimized for Series X|S". `tests/content/fixes.test.mjs` holds a list of terms and runs it over every record, `reveal` and to-do (source titles are the pages' own titles and stay as written); it fails when the first use of one comes first.
- **Dates as dates.** A relative date is written as the date. Japan's PlayStation codes expire 170 days after launch (19 November 2026), which is 8 May 2027; the answer says so, from Rockstar's page, which gives the 170 days and launch as the start.
- **Tense.** A record never speaks of a date on or before its `checked` date as still to come. `scripts/check-dates.mjs` (`npm run check:dates`, in `npm run check`) fails a sentence that holds such a date and a future cue (will, would, due, expected, coming, ...); a test plants a violation.

## Refresh

`docs/refresh.md` holds the instructions an agent follows to refresh the content: re-check the sources of the oldest records, look for new most-asked questions and known problems, add or correct records, update `rank`, write an entry for the New screen, run the checks, and push a branch named `refresh/<date>`. A GitHub Actions workflow opens a pull request for any `refresh/*` branch and merges it when the checks pass. The same instructions serve the daily cloud run and a run by hand.

## Checks

`npm run check` runs all of these, and CI runs it on every pull request:

1. **Schema.** The build fails on a record missing a source, a date, a tier or a confidence.
2. **Console text.** `scripts/check-console-text.mjs` fails on a record that shows a console another console's name or buttons (see "Rules the schema or the checks enforce").
3. **Spoiler leak.** A script takes every hidden string (see "Data shape") and fails, naming the file and the record, if it appears in any built file other than that tier's explicit-show pages and `/h/<tier>/` files: a gate page is searched with its title, meta tags and attribute values, not only its text. It also fails if the default search index or the offline list names a hidden record, or if any page prefetches a hidden address or carries `speculationrules`. It also fails when an outside map hostname or site name (read from `src/data/outside-maps.js`) appears in any built file other than `/places/**/show/**` and `/h/places/**`, scripts included (see "Links out").
4. **Dates.** `scripts/check-dates.mjs` (`npm run check:dates`) fails a record that speaks of a past date as still to come (see "First content", Tense). **Answer links.** `scripts/check-answer-links.mjs` (`npm run check:answer-links`) fails a pointer to another answer without a link and a to-do without a how-to (see "First content", Pointers). **Plain words.** `scripts/check-plain-words.mjs` (`npm run check:plain-words`) fails a listed jargon term whose first use on a page, in a script string or in a record text has no plain words in its sentence (see "First content", Plain words). **Facts.** `scripts/check-facts.mjs` (`npm run check:facts`) fails a card that states a record's facts without a source link, a date and a label on it or on the answer it links (see "Screens", Places).
5. **Behaviour**, in Playwright at 390, 820 and 1440 wide: each of the top 20 answers is reached in two taps from `/`; a ticked to-do survives a reload; the dial at Off shows no places and at Places shows them; a typed explicit address at Off lands on its gate, and at Places the places pages open while mild ones go back to their gate; the theme switch works and is remembered; nothing scrolls sideways; the main flows work with JavaScript off.
6. **Accessibility.** Every screen, in both themes, passes two passes (`tests/e2e/a11y.spec.mjs`). The theme is forced two ways at once, the stored setting and the browser's colour scheme, and the run asserts `data-theme` and the computed `--bg` are that theme's value before it measures anything. Pass one is axe, with no violations. Pass two (`tests/e2e/contrast.mjs`) does not trust axe: it settles every running fade, takes a screenshot with all text made transparent, and for every visible text node (line by line, clipped boxes and 1px hidden text left out, ancestor opacity counted) compares its colour with the pixels really painted behind it, so gradients, tints and overlays count. It fails under 4.5 to 1, or 3 to 1 for text of 24px or more (18.66px or more at weight 700). A self-check feeds it faint text and needs it flagged. A second walk in the same file, `lowNonText`, does the same for the non-text parts of controls at 3 to 1 (see "Look", Non-text contrast), with its own self-check (the old `--line` progress track). Hover and pressed tints are not on screen in a run, so `tests/lib/contrast.test.js` holds those pairs by token (see "Look"). Why the old run missed the day trouble: at rest nothing was under 4.5 to see (see "Look", Day contrast), and axe cannot judge a pressed tint or a text in mid-fade.
7. **Speed.** Lighthouse on the deployed address scores 100 for performance, accessibility, best practices and SEO on mobile, with largest contentful paint under 1 second. This one runs against the live site, outside `npm run check`.

Tests assert what a player sees, never internals.
